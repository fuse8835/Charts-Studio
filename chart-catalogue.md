# Chart Catalogue

Master reference for the Fraser Institute climate chart video series. One entry per chart. Update this file whenever a chart is added, renamed, or its design/pacing is revised.

Design system (applies to all charts unless noted): dark navy background (~#032C4E), Bright Turquoise `#04FFBA` primary data color, Vivid Blue `#043FC5` secondary accent, Rajdhani font. Export: transparent background, transparent rounded corners, ProRes 4444 alpha `.mov` (`prores_ks`, `-pix_fmt yuva444p10le`, `-bits_per_mb 1222`, `-alpha_bits 8`), 1920x1200, 30fps, ~500-550MB per 8-13s clip. Two codec swaps (HEVC-with-alpha via `avconvert`, GoPro CineForm) were tried on 2026-08-21 and both failed real After Effects import despite passing every automated test. The actual fix (2026-08-24) was tuning ProRes 4444's own encoder settings instead — the hardware encoder (`prores_videotoolbox`) had been running at ~3x Apple's nominal ProRes 4444 rate, plus using unnecessarily high 16-bit alpha precision. An initial pass at `-bits_per_mb 200` introduced visible banding on smooth background gradients (missed by verification that only checked sharp text); 1222 — Apple's own nominal 4444 rate — is the lowest value confirmed clean. Same codec throughout, confirmed working transparency in a real After Effects import. See the `chart-hevc-alpha-encoding` memory for the full history.

**Pacing standard (locked 2026-08-25, established on 1A):** every chart's reveal should run slow enough to see each value populate and each grid line draw in individually — no instant/snap-in state changes. **Grid line draw direction is bottom-left-origin:** horizontal gridlines draw left-to-right (`x1` at the left edge), vertical gridlines draw bottom-to-top (`y1` at the baseline/bottom, `y2` at the top) — for an SVG `<line>`, draw direction always runs from `(x1,y1)` toward `(x2,y2)`, so this is set purely by which end is tagged x1/y1 vs x2/y2. Apply to all new charts and when revising existing ones with gridlines.

**Chart Studio:** [index.html](index.html) is a landing page listing every chart below with an "Open chart" link and a "Render .mov" button; the same render button also appears on each chart's own page next to Replay. Both call a local render server (`_render/server.js`, registered as the `chart-studio` launch config on port 8793) that runs the exact headless-Chrome-capture + ffmpeg-encode pipeline used throughout this project, streaming live progress ("Capturing frame X/Y...", "Encoding...") back to the button. Start it with `node _render/server.js` from this directory (or the `chart-studio` launch config), then visit `http://localhost:8793`. Chart files are named by catalogue ID (`1a-*`, `1b-*`, `2a-*`, `2b-*`) specifically so the landing page and file system stay in the same order as this catalogue — keep new charts' filenames prefixed the same way, and add an entry to `_render/charts.json` plus a `<script src="render-client.js" data-chart-id="...">` tag at the end of the file for the render button to work.

### 2C — Cold-Related Death Percentage (tentative ID)
- **Subject:** A 1080×1080 split-flap "flip clock" style counter, cascading down from 63% to 06%. Reuses 2B's exact headline copy ("Deaths in the US and Canada Related to Cold and Heat Exposure, 2000-2019") plus a secondary uppercase label ("Percentage of Cold-Related Deaths"), matching two reference images Kevin provided (a photoreal mechanical flip clock, and a flatter/simplified cyan-glow card style) — **note the 63%→06% values themselves are taken directly from Kevin's reference images as given, not independently derived or verified against 2B's underlying data**; confirm the real intended percentage(s) before treating this as final.
- **Files:** [2c-cold-death-percentage.html](2c-cold-death-percentage.html) · 2c-cold-death-percentage-alpha.mov (not yet rendered)
- **ID/placement is a guess, not confirmed:** built as a companion piece to Script 2 (2A/2B) since it reuses 2B's dataset framing/copy, but Kevin didn't assign an ID — flag if it should be numbered/placed differently, filename and catalogue ID are trivial to change.
- **First chart needing a non-16:10 canvas:** every prior chart uses the shared `.frame { aspect-ratio: 16/10 }` matching the render pipeline's previously-hardcoded 1920×1200 Playwright viewport. This one needed a literal 1080×1080 square, so `_render/server.js`'s viewport is now **per-chart**: `chart.width || 1920, chart.height || 1200`, read from new optional `width`/`height` fields on the chart's `_render/charts.json` entry (2C's entry sets both to 1080). Every other chart entry omits these fields and is completely unaffected (falls through to the old 1920×1200 default) — verified by confirming the CSS clamp() sizing at the *exact* 1080px export width via `?export` + a resized viewport before ever touching the render pipeline, per the [[chart-video-export-responsive-sizing]] lesson.
- **Flip mechanic — real split-flap digits, not a shared card:** each digit (tens, ones) is its own independently-animating column, built as a stack of layered "flap" divs — one per value transition in the full countdown sequence (63,62,...,7,6 → 57 transitions for the ones digit, 6 for the tens digit, firing only when the tens digit actually changes, in sync with whichever ones-transition crosses that ten's boundary). Later flaps sit at a higher z-index and, once their own `animation-delay` elapses, snap into place and stay there (`animation-fill-mode: forwards`), permanently covering every layer beneath — so at any scrub position the composite stack always shows the mathematically correct value with no per-frame JS needed, fully seekable via `document.getAnimations()`.
- **Real bug found and fixed during build: true 3D `backface-visibility` flip breaks down at ~20+ stacked layers.** The first implementation used a literal 3D card-flip per layer (`rotateX(0deg) → rotateX(-180deg)`, front/back faces with `backface-visibility:hidden`) — correct in isolation (verified with standalone 3/10/20/35/57-layer test stacks, all rendering cleanly), and every layer's computed `transform`/`opacity` checked out exactly correct via direct inspection at rest — but the *real* 57-layer ones-digit column rendered as an unreadable glowing smear of overlapping glyph fragments. Root cause never fully isolated (ancestor `filter`, ancestor `opacity`, and cloning the real element out to a bare `<body>` root were all ruled out as the cause via targeted tests; the animation *state* was proven correct at every layer) — it's a genuine paint/compositing bug in this many independent `backface-visibility` 3D contexts stacked at once, not a logic bug. **Fix: dropped 3D entirely.** Each flap is now a single 2D layer (`opacity`/`scaleY` "snap into place" via `@keyframes flapIn`, no `perspective`, no `backface-visibility`, no front/back split) — visually reads as a flap landing, is measurably more robust (plain 2D transform+opacity has no equivalent layer-count ceiling), and is simpler code besides. **Any future flip-clock/split-flap style build in this project should start from the 2D snap technique directly** rather than re-deriving this the hard way.
- **Status:** Built and verified in live preview at the true 1080×1080 export size (`?export` query, matching the real render pipeline's URL). Scrubbed t=0.5s (63%, no caption yet), t=3.0s (39%, mid-cascade, tens/ones both correct), t=7.3s (settled at 06%, caption visible) — all render clean digits, no ghosting. Not yet rendered to video.
- **Last revised:** 2026-09-01

### 4A — The Expanding Bull's Eye Effect
- **Subject:** Why the same hypothetical flood causes far more damage to a growing city over time — the same river/terrain shown four times (1950, 1980, 2010, 2040) with concentric exurban/suburban/urban rings growing to represent the expanding city
- **Files:** [4a-bullseye-effect.html](4a-bullseye-effect.html) · 4a-bullseye-effect-alpha.mov (not yet rendered)
- **Structure:** Single scene, not a data chart — a 2x2 grid of four map panels (1950/1980/2010/2040, matching the reference's own layout), all visible at once. The river/terrain background is identical in all four panels (same location across time), fading in once; the three colored rings then grow in one time-period at a time (1950 first, 2040 last), each a quick scale-in from zero. Legend row at the bottom (Rural/Exurban/Suburban/Urban/Reservoir-Waterway/Flood Zone) fades in early, before the rings, so the color key is established before it's needed.
- **Data source:** No source SVG exists for this one — Kevin provided a reference PNG (and later a high-res crop of just the 2040 panel) plus a one-paragraph script excerpt. The map illustration is an original recreation built to visually match the reference, not a data extraction — flagged explicitly since every other chart in this series has had an exact vector/data source. Ring radii per year are estimated proportionally from the reference image, not measured.
- **Map detail pass, round 1 (2026-08-26):** rebuilt after Kevin sent a close-up of the 2040 panel — replaced the single-bend river with what read as a fork at that zoom level, and replaced the dot-pattern texture with real street-grid lines + building rectangles. Per Kevin's own suggested approach: the building/street layout is generated **once** (a seeded deterministic PRNG, so it's reproducible, not random per render) and reused via SVG `<use>` in all four panels, each just clipped to that year's exurban radius — so all four panels show literally the same underlying city, with smaller years simply revealing less of it. This `<use>`-template approach held up through round 2 below and should be the standard way to handle "same shape, four sizes" texture in any future chart like this.
- **Map detail pass, round 2 (2026-08-26) — corrected against Kevin's own `map.svg`:** Kevin then supplied a full hand-drawn reference (`map.svg`, a large auto-traced/messy file not worth parsing directly — rendered it in-browser to read visually instead of extracting path data). That reference showed the "fork" read from round 1 was actually a **single continuous winding river** (an S-curve with two bends, no branch) — corrected accordingly. Also added: a small detached oxbow pond near one bend (visible in Kevin's reference), two straight rural highway lines that cross the *entire* panel unclipped by the city circle (visible extending well past the exurban ring in the reference), and a denser/more regular street grid (block size 16→12, tighter jitter, occasional empty lots for texture variation) to match the reference's tighter grid.
- **Map detail pass, round 3 (2026-08-26) — `mpa2.svg`, and a real structural change:** Kevin rebuilt the reference himself (`mpa2.svg`, single winding river confirmed, street grid rotated ~22° rather than axis-aligned — adopted that rotation) and asked for two behavior changes: (1) each of the four panels now has its **own independently-generated city template** (`buildCityTemplate(id, radius)`, same seed every time so all four read as the same city at different sizes, not four unrelated layouts) sized so the street grid fills exactly that year's exurban circle edge-to-edge — replacing the earlier approach of one fixed-scale template just clipped smaller, which showed a smaller *crop* of the same-size blocks rather than a smaller *city*; (2) the map (terrain, river, oxbow, highways, city texture) is now static from frame 0 with no fade-in at all — only the three colored rings animate in. Building/street density, river curve, and highway placement are all still estimated by eye — there's no exact data to extract from any of the three reference images provided so far.
- **New palette (client's own legend, added as accents alongside the existing system):** `--rural-200`/`--rural-400` (light/dark green land), `--suburban-500` (red ring), `--urban-500` (yellow ring), `--water-400` (#3ea8e0 river), `--flood-200` (#bdeef2 flood band). Exurban ring uses a dedicated `--ring-blue` token rather than reusing `--vivid-500`, so retinting the ring can no longer accidentally recolor the pins/buttons/UI chrome that also read `--vivid-500`.
- **Map assets, round 4 (2026-08-31) — Kevin's own authored SVGs, replacing all procedural generation:** Kevin hand-built four separate files (`Map components/terrain.svg`, `river.svg`, `flood water.svg`, `city.svg`) that all share one native 1451.5×773 coordinate space, meant to be layered directly on top of each other as a single unified map. This replaced *all* prior procedural geometry (the estimated river curve, terrain blobs, oxbow, highways, and per-year generated city template) — every visual element in the map is now this real authored artwork.
